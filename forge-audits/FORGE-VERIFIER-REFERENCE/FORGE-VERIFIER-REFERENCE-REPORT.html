3. Tree Model

readCommit liest Raw-Commit-Header mit genau einem Tree und expliziten Parent-IDs. readTree dekodiert tatsächliche Tree-Objektbytes einschließlich unveränderter Namensbytes, Mode und 20-Byte-Objekt-ID. collectTree läuft iterativ, cached einzelne Trees und sortiert Leaves byteweise.

Jeder Eintrag enthält raw path bytes als Base64, Display-Pfad, Mode, Objektart und Objekt-ID. Symlink bleibt ein 120000-Blob; Gitlink ein 160000-Commit, niemals ein angeblicher Blob. Duplikate, malformed objects, übergroße einzelne Objekte, Tiefe und bounded History fail closed. Rohdaten sind die Identität; Display-Strings sind keine Materialisierungsschlüssel bei ungültigem UTF-8.

Ein absichtlich malformed Tree mit derselben Datei-/Verzeichnis-Komponente wird vor Export abgelehnt. Ein gültig kodierter Tree mit A/x und a/y wird ebenfalls vor dem ersten Dateisystem-Write abgelehnt. Ergebnisse in results/boundaries.json.

4. Diff

Union der Byte-Pfad-Maps; ADD, DELETE, MODIFY und MODE_CHANGE. Bei geändertem Inhalt plus Mode werden beide Flags erhalten. Kein Rename-/Copy-Score, kein git merge-tree, kein HEAD-Checkout, kein Diff-/Merge-/Textconv-Treiber.

5. Path Safety

Full-Tree-Prüfung für Base und Head. Reject: ungültiges UTF-8, C0/DEL einschließlich CR/LF/TAB, leere/absolute/backslash Pfade, . / .. / .git, portable Case-Fold-/NFC-Kollisionen einschließlich Directory-Prefix-Aliases, Datei-/Verzeichnis-Prefix-Kollisionen, Windows-Gerätenamen, trailing dot/space, ADS-Doppelpunkt, überlange Pfade und andere als gewöhnliche Blob-Modi 100644/100755.

Exklusiver Export in ein frisches privates Ziel: vollständige Pfadvalidierung zuerst, dann O_EXCL/O_NOFOLLOW. Kein Symlink-/Gitlink-Export. Ein Executable-Bit ist ein Tree-Fakt und löst keine automatische Ausführung aus; Developer-Modeänderungen sind durch Scope abgelehnt.

Bewusste False Positives: gültige Linux-Dateien wie AUX.txt, a:b, trailing space, Case-Fold-Aliases (auch Straße/STRASSE) und lange Pfade werden abgelehnt. Ein einzelner normaler Unicode-Pfad ist erlaubt, kann aber im heutigen ASCII-Format-1-Scope nicht allgemein authorisiert werden. Dieser Validator ist kein vollständiger Simulator aller NTFS/macOS-Aliase oder homoglyphischer Namen. 33 zusätzliche Boundary-Proben, einschließlich echter Export-Verweigerung.

9. Execution

EXECUTION_ISOLATION_NOT_TESTED. Docker/Container-Laufzeit war nicht verfügbar. Ein lokaler Host-Supervisor ist implementiert, jedoch ohne Sandbox, readonly mounts, Netzsperre, PID-/RAM-/CPU-cgroups oder Schutz gegen bösartiges JavaScript. Die harmlosen Fixtures liefen bewusst lokal; der CLI verlangt dafür --unsafe-local-lab.

Readonly Trusted-Tests/Dependencies sind hier logisch gepinnt, aber als Host-Dateien nicht gegen untrusted Prozesse abgeschirmt. Pipeline-Report-PASS ist deshalb nur funktionales Laborverhalten; kein Beweis für sichere produktive Ausführung.

Eine O(changes × scope)-Listensuche wurde vor dem finalen Modell durch Sets ersetzt. Separater Microbenchmark bei 10.000 Einträgen: List-Membership ~413 ms gegenüber Set-Aufbau+Membership ~0,90 ms auf diesem Host. Das ist ein mechanismischer Vergleich, keine harte Performance-Garantie.

15. Differential Corpus

Wichtigstes Deliverable: results/differential/cases.json zusammen mit 150 repos/*.git. Jede Case hat input manifest, echte Base/Head-IDs, erwartete canonical changes, Gate-/Verify-Soll und primären Failure-Code. Der Black-box-Adapter ruft gate und verify mit Manifest/Repo auf und prüft externes JSON sowie Exitcodes. Aktuell 300 CLI-Vergleiche, 0 Unterschiede. Die nächste produktive Implementation wird über einen kleinen Adapter auf denselben Eingaben geprüft. Ein zweiter Differential-Korpus für echte Container-Ausführung/Report-Provenienz bleibt separat erforderlich.

Reproduzierbare Determinismusmerkmale: feste Commit-Zeit/Identitäten, explizite raw paths, gleiche source bytes, feste seeds, keine Zeitstempel im diff. Package-Datei-Hashes erleichtern Integritätsprüfung; sie sind keine Signaturen oder Reviews. Das corpus profile muss owner-reviewed werden, bevor seine neuen Lab-Codes normative Produktionsbedeutung bekommen.

16. Known Limits

  • Execution isolation fehlt ausdrücklich; keine Autorität für untrusted production runs.
  • GitHub Rulesets/Actions-/native Check-/Re-run-/Merge-Serversemantik wurde nicht geändert oder live geprüft. Metadata fixtures sind Eingabemodelle.
  • Trusted policy/contract/review provenance wird vorausgesetzt; kein ForgeLog-Lifecycle-Replay, keine komplette Contract-Registration-/Owner-OPS-Pipeline oder GitHub-Review-Auswahl implementiert.
  • Core Format 1 hat keine reads/limits/concrete-mutants-Felder. Auxiliary policy ist lokale Laborsemantik; kein Format 2.
  • Keine universelle JSON.stringify/Zod-Äquivalenz, kein vollständiges Windows-Dateisystemmodell, keine arbitrary-input/resource-exhaustion-Garantie.
  • Fetch pack/transfer memory hat hier keine harte Byte-/RAM-/PID-Grenze. Git-, Python-, Node-/Toolchain-Binaries bleiben TCB.
  • Untrusted JavaScript kann Tests, Reporter und Host-Dateien manipulieren. Inventar und Mutanten liefern begrenzte Verhaltensnachweise, keinen Vollbeweis der Testqualität oder Report-Ehrlichkeit.
  • Die bisherigen historischen B-v2-sidecar-/acceptance-/RT-12-/Performance-Grenzen werden nicht durch dieses Labor repariert.

Engineering-Negativversuche wurden nicht als PASS ausgegeben: fehlender Node-Pfad in gesäuberter Umgebung (behoben durch supervisor-owned runtime path), malformed-policy AttributeError (definierter FAIL + Regression), Git verweigert malformed Tree beim normalen Schreiben (Fixture-Generator nutzt ausdrücklich --literally), fehlender Netzwerkproxy (separate Fetch-Allowlist), Wiederholungsziel beim wrong-pin-Test (idempotenter Fixture-Cleanup), früh abbrechender Contract-Error ohne vorhandenen Diff (Diff bleibt nach Collection erhalten).
