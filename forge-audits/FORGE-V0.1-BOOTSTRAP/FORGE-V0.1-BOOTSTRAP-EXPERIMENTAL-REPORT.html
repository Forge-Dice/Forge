Read-only Remote-Labor · 3. Oktober 2026 · Forge-Dice/Forge

Ergebnis: GO für die lokale Verifier-Implementierung und einen isolierten Live-Drill; NO-GO für die Behauptung, der kanonische Bootstrap sei bereits sicher aktiviert. Die wichtigsten lokalen Fragen sind durch reproduzierte Experimente beantwortet. GitHub-Schreib-, Merge- und Bypass-Verhalten wurde nicht live verändert oder getestet.

Entscheidungen: H1 REMOVE. H2 getrennte, bypassfreie Lösch-/Force-Push-Sicherung. H3 ein trusted PR-Workflow ohne Dispatch, Owner-Recheck über Re-run all jobs. Sieben Branch-/Tag-Rulesets plus eine repositoryweite Actions-Ausführungspolicy sind die hier kleinste nachvollziehbar begründete Kombination bei zusätzlichem Owner-only-Merge und gesperrtem direktem Owner-main-Push. Eine Reduktion auf sechs würde in dieser Zerlegung eine Garantie aufgeben oder eine gleichwertige weitere Schutzschicht verstecken.

2. H1 Result

Entscheidung: REMOVE require_last_push_approval.

DOCUMENTED: GitHub beschreibt diese Option als notwendige Freigabe durch eine andere Person als den letzten Pusher. required_approving_review_count und require_last_push_approval sind eigenständige API-Parameter. Eigene PRs können vom Autor nicht selbst mit einer zählenden Approval freigegeben werden. [S1, S2, S15]

INFERRED für die exakte Kombination: required approvals=0 hebt die zusätzliche Last-Push-Bedingung nicht auf. Bei Owner als PR-Autor und ohne irgendeine andere Approval ist ein regulärer Merge unter wirksamer Last-Push-Regel nicht möglich. Owner als letzter Pusher scheitert zusätzlich unmittelbar an „someone other than“. Ein Admin-/Owner-Bypass wäre ein Bypass, kein regulärer Erfüllungsweg. Eine externe AI-Review-Attestation zählt nicht als GitHub-Approval.

UNKNOWN / nicht LIVE VERIFIED: Ob die konkrete aktuelle GitHub-UI die Kombination 0+true direkt speichert und die exakte serverseitige Blockiermeldung. Es gibt hier keinen verfügbaren Repo-Erstellungs-/Admin-Experimentpfad für ein unabhängiges GitHub-Testrepository. Es wurde deshalb keines angelegt. Lokale Git-Simulation kann GitHubs Review-Engine nicht beweisen.

Technische Folgerung: native Approvals 0, Last-Push false, Codeowner-Approval false für diesen Single-Owner-Pfad. Owner-Attestation wird vom Verifier an {repo, PR, base, head, contract, verifier, AI-report} gebunden. CODEOWNERS kann Orientierung liefern, darf aber nicht unbemerkt eine erneute Selbstfreigabe-Sperre einführen.

3. H2 Result

DOCUMENTED: Bypass gilt innerhalb eines Rulesets. Mehrere passende Rulesets wirken gemeinsam; ein Bypass in der Namespace-Schreibregel beseitigt nicht eine unabhängige bypassfreie Löschsperre. [S1–S3]

INFERRED: Die häufige fehlerhafte Kombination lautet: „Restrict updates + Restrict deletions“ in einem Ruleset mit forge-codex: always bypass. Derselbe Bypass erlaubt dann auch Löschen. Deshalb universelle Regeln und Actor-Schreibregeln trennen.

V0.1-Entscheidung: Force-Push in allen Branch-Namespaces verbieten. Die Ein-Commit-Form eines Contracts benötigt keine umgeschriebene bereits gepushte Branch-Spitze: jede Revision erhält einen neuen Branch, etwa forge/contract/CORE-0002-v2. Ein Commit pro Revisionsbranch; alte Branches bleiben erhalten. Vor dem ersten Push darf lokal natürlich amendiert werden. Das spart eine separate Ausnahme-Schicht.

Falls „dieselbe Contract-Branch muss nach jeder Revision wieder exakt einen Commit haben“ verbindlich ist, wird Force-Push dort technisch erforderlich. Dann universelle Löschsperre separat halten, globale Force-Push-Sperre ohne Contract-Namespace, und eine eigene Contract-Force-Push-Regel mit exakt dessen zulässigem Autor ergänzen. Das ist mindestens eine weitere Regelgruppe; nicht heimlich in einen allgemeinen Bypass packen.

EXPERIMENTALLY VERIFIED: Das lokale 7-Regel-Modell prüft Cross-Namespace-Schreiben, Merge-Akteure, Lösch-/Force-Push-Invarianten und Tag-Sperre. Entfernen jedes einzelnen Rulesets erzeugt ein Gegenbeispiel. Das belegt die Konsistenz dieses Modells, keinen mathematischen Minimalitätsbeweis über sämtliche GitHub-Produkte und keinen Live-Server-Test.

„Niemand“ gilt für Ref-Operationen bei unveränderter Schutzkonfiguration. Ein Repository-Admin kann Schutzkonfiguration ändern; Branch-Rulesets können ihrem Administrator nicht die Administration entziehen. Auch das Löschen des gesamten Repositorys ist nicht durch eine Branch-Löschsperre abgesichert.

4. H3 Result

DOCUMENTED: workflow_dispatch kann eine ausgewählte Branch-/Tag-Version verwenden. Ein Owner-Check allein im YAML auf einer Developer-veränderbaren Branch ist daher keine unabhängige Sicherheitsgrenze. Reusable Workflows erben den Event-Kontext; ein zweites Wrapper-YAML behebt dieses Grundproblem nicht. [S4, S5]

Design Trusted Source / Event Token / Actor / Attribution Komplexität und Urteil
A: PR-target + Dispatch in einem Workflow PR-target: Default-Branch; Dispatch: gewählter Ref YAML-Actor-Guard auf manipulierbarem Dispatch-Ref entfernbar; Dispatch-Jobchecks sind keine verlässliche PR-Pflichterfüllung Klein auf Papier, zusätzliche externe Event-/Actor-Policy erforderlich. Für V0.1 verwerfen.
B: PR verifier + Owner recheck Nur echte Plattformkontrolle schützt separaten Dispatch-Wrapper Zwei Dateien trennen Bedienung, nicht automatisch Rechte; doppelte Checknamen riskant Mehr Oberfläche ohne Bedarf. Verwerfen.
C: beide Wrapper → reusable Reusable muss immutable/trusted referenziert und Caller geprüft werden Keine automatische Owner-only-Garantie; Caller-/Permissions-/Event-Validierung nötig Drei Workflow-Dateien statt einer. Verwerfen.
D: workflow_run / check-suite Default-Branch-Finalizer möglich; vorgelagerter Run bleibt untrusted Privilegierte Weiterverarbeitung und Artefakt-Provenienz müssen abgesichert werden; Check-Suite-Rekursion eingeschränkt Für externen Publisher sinnvoll, für diesen kleinen V0.1 unnötig.
Gewählt: nur PR-target, Re-run all jobs Ein Default-Branch-Workflow, ein Event-Typ Beide Jobs permissions: {}, keine Credentials, kein Dispatch Kleinste hier vorgeschlagene sichere Variante unter untenstehenden Plattform- und Execution-Annahmen.

DOCUMENTED, wichtig für Oktober 2026: GitHub beschreibt inzwischen repositoryweite Actions-Ausführungspolicies für öffentliche Repositories. Sie können erlaubte Events und Akteure außerhalb des YAML begrenzen. [S6, S7]

INFERRED, zwingende Voraussetzung: Eine aktive Policy für alle Workflows, keine Path-Ausnahmen: ausschließlich pull_request_target; Actor-Allowlist Wuerfelduell und forge-codex mit numerischen IDs. Dadurch sollen Developer-push-/pull_request-/Dispatch-Workflows bereits vor Ausführung blockiert werden. Alle auf main vorhandenen PR-target-Workflows bleiben Teil der trusted computing base; keine unerwarteten weiteren Workflows.

Ohne diese Voraussetzung kann ein Developer auf seiner zulässigen Branch einen neuen push-Workflow anlegen. Stage 1 lehnt den PR zwar ab, aber zu spät, um den Workflow-Start zu verhindern. Auch ein GitHub-Actions-App-Pin für Checknamen unterscheidet dann nicht zwischen vertrauenswürdigem und eingeschleustem Actions-Workflow. Ohne wirksame Plattformpolicy: NO-GO für dieses Design.

UNKNOWN: Effektive Actions-Policies in Forge-Dice/Forge und Live-Verhalten von Re-runs unter der neuen Policy. Die Dokumentation kündigt für betroffene öffentliche Repositories eine Default-Blockierung von PR-target zum 2. November 2026 an; die benötigte explizite Event-Zulassung und etwaige übergeordnete Restriktionen müssen vor Aktivierung geprüft werden. [S8]

5. Trusted Checkout

EXPERIMENTALLY VERIFIED: git_lab.py erzeugte ausschließlich lokale Wegwerf-Repositories. Enthalten: Replacement-Ref, Merge-Commit, Symlink, Gitlink, executable bit, Rename, Delete, leere und binäre Datei, Unicode-Pfad mit Zeilenumbruch/Tab, case-only Rename und gleichzeitige A.ts/a.ts-Dateien. Marker zeigen, ob ein konfigurierter Treiber ausgeführt wurde.

Operation Lokales Resultat / sichere Verwendung
GIT_NO_REPLACE_OBJECTS=1 Liest ursprüngliche Objekte. Ohne Flag konnte refs/replace den Head wie den Base-Tree aussehen lassen. Alle Git-Prozesse müssen dieselbe gesäuberte Umgebung erhalten.
git cat-file -t SHA, git cat-file -p SHA, git cat-file blob OID Rohobjekte/Typen lesbar, kein Checkout. Nicht --filters oder --textconv verwenden.
git ls-tree -r -z --full-tree SHA Vollständige Tree-Einträge; NUL-sicher. Symlink = 120000 blob; Gitlink = 160000 commit.
git diff-tree --no-commit-id --raw -r -z --no-renames --no-ext-diff --no-textconv BASE HEAD Expliziter Tree-Paarvergleich geeignet. Ein einzelner Merge-Commit mit Default-Diff lieferte dagegen keine Änderungsausgabe.
git diff --raw --no-abbrev -z --no-renames --no-ext-diff --no-textconv BASE HEAD -- Geeignete zusätzliche Gegenprüfung. Keine externe Diff-/Textconv-Ausführung im Versuch.
git merge-base --is-ancestor BASE HEAD Geeignet in vollständiger, sauberer ODB. Fehlender Ancestor oder shallow/graft metadata: fail closed.
git merge-tree --write-tree BASE HEAD Sauberer einfacher Versuch erfolgreich. Zweiter Versuch mit divergierenden Trees und konfiguriertem Merge-Treiber führte diesen aus. Nicht als inhärent ausführungslos behandeln. Für V0.1 entfallen lassen.
objects/info/alternates Wird auch bei gesäuberten Umgebungsvariablen weiterhin berücksichtigt. Umgebungsreinigung allein reicht nicht.
Blob-Materialisierung Base ohne Git-Checkout materialisiert; gefährlicher Head vor Materialisierung abgelehnt. Keine Symlink-/Gitlink-Auflösung.

INFERRED: minimaler Erwerbs-/Exportvertrag. Neues leeres, verifier-eigenes Bare-Repository; leeres Template-Verzeichnis; keine lokale Kopie fremder .git, kein --shared, --reference, Submodule oder LFS-Schritt. System/global Git-Konfiguration deaktivieren, Umgebung per Allowlist, GIT_NO_REPLACE_OBJECTS=1, GIT_NO_LAZY_FETCH=1, Hooks /dev/null, keine Credential-Helper und keine HTTP-Extraheader. Feste HTTPS-Remote, nur main und refs/pull/<Integer>/head, --no-tags --no-recurse-submodules. SHA mit voller 40-stelliger Hex-Syntax prüfen, Fetch-Ref-Ergebnis gegen erwarteten SHA vergleichen; jede Abweichung/Unvollständigkeit abbrechen.

Lokale config, include*, alternates, grafts, shallow-/promisor-Metadaten explizit ablehnen. Fetch enthält Objekte, nicht die .git/config des Autors. Trotzdem muss das lokal erzeugte Repository unter alleiniger Kontrolle des Verifiers bleiben. .gitmodules und .gitattributes sind zunächst nur Blob-Daten und werden weder ausgeführt noch für einen Checkout interpretiert.

Materialisierung erst nach Full-Tree-Validierung: Pfade als Bytes parsen; ungültiges UTF-8, Kontrollzeichen, ./.., .git, Case-/Unicode-Normalisierungs- und Datei/Verzeichnis-Kollisionen für V0.1 ablehnen. Nur genehmigte 100644/100755-Blobs, frisches Ziel, keine Symlinks, exklusives Öffnen ohne Link-Following. Executable-Bit nicht automatisch ausführen. Limits für Objekte, Dateien, Gesamtbytes, Tiefe und Zeit. Keine Annahme, Git selbst sei immun gegen Parserfehler.

Trusted Verifier-Dateien kommen aus dem gepinnten main/Base-SHA, Head ausschließlich als Daten in Stage 1 und als Testgegenstand in Stage 2. Für V0.1 verlangt die Policy BASE == aktuelles main == verifier source und BASE als Ancestor von HEAD; kein unbeprüfter synthetischer Merge-Tree. Git-Dokumentation bestätigt das Replacement-Flag; die oben beschriebenen Verhaltensbefunde stammen aus dem Labor. [S9]

6. Canonical Diff Collector

EXPERIMENTALLY VERIFIED: prototypes/collect_diff.py implementiert den minimalen Object-Collector. Zwei ls-tree -r -z-Maps, byteweise sortierte Pfadunion, Vergleich von Modus und Objekt-ID. Kein Checkout und keinerlei Rename-Heuristik.

interface Change {
  path: string;          // Anzeige; niemals die einzige Identität
  pathBase64: string;    // originale Git-Pfadbytes
  types: ('ADD'|'MODIFY'|'DELETE'|'MODE_CHANGE')[];
  oldMode: string|null; newMode: string|null;
  oldBlob: string|null; newBlob: string|null;
  oldObject: string|null; newObject: string|null;
  oldType: 'blob'|'commit'|null; newType: 'blob'|'commit'|null;
}
Testfall Kanonisches Ergebnis
Gewöhnliche Änderung MODIFY, beide Blob-IDs
Hinzufügen / leere Datei / Binary / Unicode ADD; leere Datei hat eine reale Blob-ID, kein null
Löschen DELETE
Rename DELETE old + ADD new, auch bei gleichem Blob
Case-only Rename DELETE Case.ts + ADD case.ts
Nur executable bit MODE_CHANGE, Blob-ID unverändert
Inhalt und Modus geändert Zwei Flags: MODIFY und MODE_CHANGE; keine Information geht verloren
Symlink ADD mit Modus 120000 und Linktext-Blob; Gate lehnt Modus ab
Gitlink ADD mit Modus 160000 und Commit-ID; newBlob=null, newObject=commit SHA
Case-Kollision Beide Pfade sichtbar; kein Überschreiben beim Collector; Gate muss Export ablehnen

Der eigenständige Collector wurde gegen den adversarial Tree und PR #2 geprüft. Wiederholung ergab identisch sortierte Datensätze. Byte-identische Evidence-Digests erfordern zusätzlich festgelegte JSON-Kanonisierung; Zeitstempel nicht in den kanonischen Diff aufnehmen. Die Scratch-Commit-SHAs sind wegen Commit-Zeiten bei erneuter Fixture-Erzeugung nicht konstant; die Assertions und Änderungstypen sind reproduzierbar.

Imports können Framework-Verhalten manipulieren, Tests können tautologisch sein, Ausgaben gefälscht werden. Unveränderte trusted Tests und Mutants erhöhen Aussagekraft; sie sind kein Vollbeweis gegen beliebigen adversarial Code.

9. Safe Execution Boundary

DOCUMENTED: Ein Standard-ubuntu-24.04-GitHub-hosted Job läuft auf einer neuen VM. Linux-Runner haben passwordless sudo; Netzwerk und gemeinsames Job-Dateisystem existieren. Das ist keine Sicherheitsgrenze zwischen trusted Verifier und untrusted Tests desselben Jobs. ubuntu-slim hat ein anderes Container-Modell und wird hier nicht verwendet. [S12]

INFERRED: kleinste vertretbare V0.1-Annahme für dieses adversarial Modell: getrennte GitHub-hosted Jobs, keine Secrets, keine Repository-Schreibrechte, keine persistenten Credentials/Caches. Zusätzlich eine explizite Execution-Grenze innerhalb Stage 2: trusted Supervisor außerhalb, Testprozess in kurzlebigem eingeschränktem Container, non-root, alle Capabilities entfernt, no-new-privileges, kein Docker-Socket/Host-PID/Host-Netz, read-only Mounts für Verifier/Toolchain/Tests/Eingaben, begrenzte tmpfs-Ausgaben, CPU-/RAM-/PID-/Zeitlimits, Tests mit --network=none. Image auf überprüften Digest pinnen. Container-Isolation vertraut dem Host-Kernel; kein Anspruch auf perfekte VM-Isolation gegen Kernel-Exploits.

Installation getrennt: gepinnte Baseline-Pakete mit --ignore-scripts in einem frischen Installationsbereich; Netzwerk nur in dieser Phase. Keine PR-Dateien als ausführbare Package-Manager-Konfiguration. Danach unveränderte Toolchain schreibgeschützt in Testcontainer. Fresh toolchain installation ersetzt Cache-Abhängigkeit.

Was eine frische VM isoliert: Zustand zu vorherigen/nächsten normalen Jobs, bei getrennten Standard-Jobs auch deren lokale Arbeitsbereiche. Was sie nicht isoliert: Schritte/Prozesse desselben Jobs, erreichbare Netzressourcen, innerhalb des Jobs vorhandene Credentials, Reports/Runner-Dateien und das System vor eigenem sudo-fähigem Code. Ein separates Unterverzeichnis ist keine Sandbox.

permissions: {} reduziert GitHub-API-Rechte des Job-Tokens. Es entfernt nicht alle Runner-Service-Credentials und ist keine Netz-/Filesystem-Sandbox. Keine Secrets referenzieren, keinen OIDC-Token anfordern, keine Auth-URL, kein persist-credentials. Tests erhalten eine neu aufgebaute Umgebung, keinen Host-Runner-Servicekontext.

UNKNOWN: Ein passendes Container-Image, dessen Digest und die GitHub-hosted Sandbox-Ausführung wurden hier nicht implementiert oder live geprüft; Docker steht in diesem Labor nicht bereit. Die durchgeführten harmlosen Testmutationen liefen lokal ohne solche Isolation. Das Labor behauptet ausdrücklich keinen bestandenen Sandbox-Drill.

10. Two-Stage Verifier

Entscheidung — INFERRED: zwei Jobs in einem Workflow.

Job Aufgaben Nicht erlaubt
forge-gate Repository/IDs, Base/Head/Ancestry, Contract, Scope, Tree-Modi, geschützte Dateien, Config-/Paketänderungen, Identität, Limits npm, Imports von HEAD, Vitest-Collection, PR-Hooks, PR-Workflow-Ausführung
forge-verify Nach erfolgreichem Gate: erneute statische Validierung auf frischer VM, Installation ohne Scripts, Typecheck, gesamte Suite, Inventarvergleich, Mutants, aktuelle Owner-Attestation und finale SHA-Prüfung Schreib-Token, Secrets, ungeprüftes Übernehmen von Artefakten, privilegierter Report-Consumer

Ein einzelner Job spart kaum YAML, teilt aber Kontrolle und Ausführung im selben Dateisystem. Zwei Jobs vermeiden diesen direkten Zugriff auf Stage 1. Stage 2 lädt Quelle und Fakten neu vom gepinnten SHA; kein Artefakttransfer notwendig. Das Job-Ergebnis von Stage 1 ist nur eine Startbedingung, ersetzt nicht das erneute statische Prüfen.

forge-verify wird mit if: always() gestartet und beendet sich explizit fehlerhaft, wenn needs.gate.result != success. Ein nur übersprungener Pflichtjob darf nicht versehentlich als akzeptabler Checkzustand wirken. Kein continue-on-error für Pflichtschritte. Laufzeitfehler, Cancellation und unbekannte Zustände sind kein PASS.

Automatischer Erstlauf kann Testresultate liefern, aber ohne passende Owner-Attestation bleibt der finale Verify-Check rot. Nach externem Review: Owner-Attestation und Re-run all jobs. Für einen ausschließlich automatischen technischen Vorcheck darf das fehlende Review im Report getrennt vom Testergebnis erklärt werden; die Merge-Gesamtentscheidung bleibt FAIL.

11. Check Semantics

DOCUMENTED: Required Checks beziehen sich auf den aktuellen Head beziehungsweise gegebenenfalls den geprüften Merge-Commit. Alte Commit-Ergebnisse reichen nicht. workflow_dispatch-Jobchecks erfüllen laut aktueller GitHub-Dokumentation keine PR-Ruleset-Checks; pull_request_target ist ein dafür berücksichtigter Event-Typ. Skipped/neutral können als erfolgreiche erforderliche Checks gewertet werden. [S13]

INFERRED Design: Genau ein Workflow mit zwei ungematrixten nativen Jobnamen forge-gate und forge-verify. Keine gleichnamigen Commit Statuses, keine zweiten Publisher, keine dynamischen Suffixe, keine weiteren Workflow-Jobs mit diesen Namen. Required source: GitHub Actions, nicht „any source“. Zusätzlich die all-workflow Event-Policy aus H3, weil App-Identität allein nicht das Workflow-YAML authentifiziert.

UNKNOWN / zwingender Live-Drill: Die tatsächlichen check_run.head_sha, check_suite, workflow_run.head_sha, PR-Zuordnung und Mergebox-Wertung von PR-target erfassen. GITHUB_SHA ist hier Default-Branch-SHA; nicht einfach behaupten, das sei der PR-Head. Explicit HEAD_SHA in Testdaten ändert keine native Check-Zuordnung. Aktuelle Dokumentation erlaubt den Event-Typ, ersetzt aber keinen Nachweis für diese konkrete Zwei-Job-/Re-run-Konfiguration.

Prüfen: PR H1 grün → H2 pushen → H1-Lauf erneut starten → H2 darf dadurch nicht mergefähig werden. Ein alter Re-run darf nur seinen gebundenen Head prüfen und muss bei Abweichung von aktuellem Head abbrechen. Parallelität pro PR begrenzen, alte Runs abbrechen; direkt vor erfolgreichem Abschluss PR/Base/Review neu lesen. Strikte Up-to-date-Checks auf main begrenzen Basisveraltung. Keine Behauptung einer atomaren Transaktion zwischen letztem GET und Merge; Owner muss beim Merge erwarteten Head SHA verwenden, wo die API das unterstützt.

Wenn native Zuordnung im Live-Drill scheitert, nicht durch einen grünen main-Check ersetzen. Dann separater vertrauenswürdiger Check-Publisher mit explizitem head_sha nötig; das wäre mehr Komplexität und eine neue Rechteentscheidung. [S14]

Wichtige Präzisierung: Rulesets verbieten nicht unbedingt, dass ein anderer write-Actor eine PR zwischen schon existierenden Branches eröffnet. Die Zeilen „Owner-PR/Codex-PR“ beschreiben zulässige Forge-Identität, nicht eine behauptete GitHub-PR-Erstellungs-ACL. Der Static Gate muss solche vertauschten Autoren ablehnen. Die Ref-Mutationen selbst werden durch R4/R5 eingeschränkt.

Gefundene Widersprüche und Auflösung:

  • Last-Push-Approval sperrt den Single-Owner-OPS-Pfad: entfernen.
  • Owner-Bypass zusammen mit Checkpflicht erlaubt Check-Umgehung: R2/R3 trennen.
  • Namespace-Bypass zusammen mit Delete-Protection erlaubt Löschen: R1 separat.
  • One-commit-Revision auf derselben Branch kollidiert mit Force-Push-Verbot: neue Contract-Revisionsbranch.
  • „Keine Workflows aus PR“ ist durch Stage-1-Pathprüfung allein nicht erreicht: Actions-Event-Policy vor Workflow-Aktivierung.
  • „Halt = Actions aus“ reicht nicht gegen bereits grüne Heads: Merge-Schreibrecht vorübergehend sperren. Eine dauerhafte zusätzliche Halt-Regel würde die Ruleset-Zahl erhöhen; der Operator-Eingriff im Notfall ist explizit und nicht im Normalmodell versteckt.

Ein Owner kann als Admin Regeln ändern und später eigene Sperren entfernen. Eine unveränderliche Garantie gegen diesen Admin selbst ist außerhalb dieser technischen Konstruktion.

18. Exact Five-Step Bootstrap

STEP 1 — Lokalen Verifier fertigstellen. Die getesteten Collector-/Inventarbausteine in trusted Code übernehmen; Static Gate, SHA-bound Owner-Attestation, Supervisor, Container-Digest, Evidence und Drill-Fixtures vervollständigen. Im lokalen Labor erneut D1–D9 und die Container-Dateisystem-/Netzgrenzen prüfen. Keine kanonischen Änderungen in dieser Berichtssitzung.

STEP 2 — Ein entbehrliches GitHub-Repository prüfen. Mit Owner- und Developer-Testidentität sieben Rulesets plus Actions-Policy exakt ausprobieren: H1 0+last-push, Bypass-Layering, Pattern-Kanten, Checks an H1/H2, Re-run, Developer-Workflow-Injection, Owner-eigene OPS-PR, Halt. Schlägt ein geforderter Pfad fehl, nicht auf Forge übertragen. Falls kein solches Repo verfügbar ist, Bootstrap bleibt NO-GO für unbewiesene Enforcement-Garantien.

STEP 3 — Kanonische Bootstrap-OPS vorbereiten und gesondert autorisiert einbringen. Schutz-/Workflow-Entwurf, Verifier, Scope-Policy, Contract und Baseline zusammen reviewen. All-workflow Event-Policy vor untrusted Workflow-Ausführung einrichten, Actor-/Namespace-Sperren aktivieren; trusted Verifier-Dateien über Owner-OPS einbringen. Die initiale Installation ist ein ausdrücklich dokumentierter Bootstrap-Zustand, kein durch bereits existierende Checks freigegebener Normalbetrieb. PR #2 nicht dafür missbrauchen.

STEP 4 — Pflichtchecks scharfstellen. Echte erfolgreiche Checknamen/App-Zuordnung erst erzeugen und prüfen, dann forge-gate/forge-verify ohne Bypass als erforderliche Checks aktivieren. Aktuelle main-Baseline inventarisieren, 1.087 nur für diesen SHA bestätigen, klassische/übergeordnete Schutzregeln abgleichen und finale Lockout-Matrix kontrollieren. Keine Lücke als „fertig geschützt“ deklarieren.

STEP 5 — Ersten echten Forge-Drill ausführen. Codex setzt nur die triviale Clamp-Änderung um; Owner attestiert externes Review für genau diesen Head, startet Re-run all jobs und mergt ausschließlich bei passenden frischen Nachweisen. Negative D2–D9 jeweils getrennt testen; keine produktive Folgearbeit vor bestandenem Drill.
