## 3. Endgültiges Datenmodell

Alle Felder sind Pflichtfelder. Alle Objekte sind strikt. Keine Defaults, Coercions, Freitext-Erweiterungsfelder oder automatisch erzeugten Einträge. Datentypen aus Zod-Schemas ableiten.

Die folgende Notation ist normativ; sie ist kein bereits vorhandener Code:

```text
NpcKnowledgeSnapshot = {
  schemaVersion: 1,
  caseId: CaseId,
  truthHash: SHA256,
  solutionHash: SHA256 | null,
  npcId: PersonId,
  revision: positive safe integer,
  asOf: Tick,
  awareness: AwarenessEntry[],
  attitudes: AttitudeEntry[]
}
```

Beide Collections dürfen leer sein. Ein NPC ist eine vorhandene Person, keine neue Entitätsklasse. Es gibt keine eigene NPC-ID und keine IDs für einzelne Einträge.

`SHA256` bedeutet exakt 64 kleine Hex-Zeichen, ohne weitere Zeichen oder Zeilenumbrüche. `Tick` übernimmt die vorhandenen nichtnegativen sicheren Ganzzahlen einschließlich Ablehnung von `-0`.

```text
AwarenessSubject =
  { kind: "person", id: PersonId }
  | { kind: "location", id: LocationId }
  | { kind: "item", id: ItemId }
  | { kind: "event", id: EventId }
  | { kind: "evidence", id: EvidenceId }

AwarenessEntry = {
  subject: AwarenessSubject,
  acquiredAt: Tick,
  provenance: Provenance
}

StatementSubject =
  { kind: "proposition", id: PropositionId }
  | { kind: "conclusion", id: ConclusionId }

EpistemicStance =
  { kind: "knowledge", value: boolean }
  | { kind: "belief", value: boolean }
  | { kind: "uncertain", leaning: boolean | null }
```

`awareness` bezeichnet einen ausdrücklich modellierten subjektiven Bezug zu einer Entität. Sie ist weder eine Freigabe aller Attribute noch ein Beleg persönlicher Bekanntschaft. Bei einem Event ist sie ein bekannter Referent, keine zusätzliche Aussage über Zeitpunkt, Ablauf oder vollständige Wahrnehmung.

```text
AttitudeEntry =
  {
    subject: { kind: "proposition", id: PropositionId },
    stance: EpistemicStance,
    acquiredAt: Tick,
    provenance: Provenance
  }
  | {
    subject: { kind: "conclusion", id: ConclusionId },
    stance:
      { kind: "belief", value: boolean }
      | { kind: "uncertain", leaning: boolean | null },
    acquiredAt: Tick,
    provenance: Provenance
  }
```

Die Einschränkung für Conclusions muss sich sowohl im Schema als auch im abgeleiteten TypeScript-Typ ausdrücken. `knowledge` ist für Conclusions in V1 immer unzulässig.

## 5. Bindungsregeln

Sei `T = hashCaseTruth(truth)`.

Für jeden NPC-Snapshot gilt:

- `caseId === truth.caseId`.
- `truthHash === T`.
- `npcId` existiert in `truth.persons`.

Wenn `solution === null`:

- `solutionHash === null`.
- Jede Conclusion-Attitude ist unzulässig, auch wenn ihre ID syntaktisch gültig ist.
- Kein Zugriff auf eine globale, zwischengespeicherte oder anderweitig implizite Solution.

Wenn `solution !== null`:

- `solution.caseId === truth.caseId`.
- `solution.truthHash === T`.
- `solutionHash === hashCaseSolution(solution)`.
- Conclusion-Referenzen werden ausschließlich in dieser Solution aufgelöst.

Die Bindung an die vorhandene Solution gilt auch für Snapshots ohne Conclusion-Attitudes. Ein nichtnull `solutionHash` kann niemals mit einem null Solution-Kontext verwendet werden.

Die Projektion prüft dieselbe Bindung vor jeglicher Freigabe erneut. Eine andere Truth mit gleicher `caseId` oder Revision reicht nicht. Gleiches gilt für eine andere Solution mit gleicher eigener Revision.

Keine automatische Umbindung und kein stilles Entfernen von Conclusions, um einen unpassenden Kontext akzeptieren zu können.

Validierungsprobleme erhalten Eingabepfade: `caseId`, `truthHash`, `solutionHash`, `npcId` beziehungsweise die betroffene Referenz. Ein zur Truth unpassender Solution-Kontext wird bei `solutionHash` berichtet. Diese Zod-Diagnostik ist ausschließlich für vertrauenswürdigen Autorencode bestimmt.

## 6. Knowledge, Belief, Uncertainty und Unwissen

| Zustand | Semantik | Prüfung |
|---|---|---|
| `knowledge, value: true` | Kenntnis des Proposition-Claims | `Proposition.truth === true` |
| `knowledge, value: false` | Kenntnis der Verneinung des Proposition-Claims | `Proposition.truth === false` |
| `belief, value: true` | NPC hält Claim für wahr | Keine notwendige Übereinstimmung mit kanonischem Wert |
| `belief, value: false` | NPC hält Claim für falsch | Keine notwendige Übereinstimmung mit kanonischem Wert |
| `uncertain, leaning: true` | Vermutung in Richtung des Claims | Keine Wahrheitsprüfung |
| `uncertain, leaning: false` | Vermutung in Richtung seiner Verneinung | Keine Wahrheitsprüfung |
| `uncertain, leaning: null` | Aussage ist Thema, keine Richtung festgelegt | Keine Wahrheitsprüfung |
| Kein Eintrag | Keine modellierte Haltung | Keine Negation und kein automatisch erzeugtes `unknown` |

Ein Irrtum ist beispielsweise `belief:true` zu einer Proposition mit `truth:false`. Er wird nicht repariert. Es gibt kein gespeichertes oder projiziertes `isMistaken`.

Ein richtiger Glaube wird nicht automatisch Wissen. `knowledge` ist ein faktives Autorenlabel mit deklarierter Herkunft, kein maschinell bewiesener Erkenntnisprozess.

Conclusion-Glaube und -Unsicherheit bleiben zulässig, gleichgültig ob die Conclusion objektiv wahr, falsch oder `undetermined` ist. TASK-0004 ermittelt diesen objektiven Status nicht. Auch `requiredConclusions` wird dafür nicht ausgewertet.

Unwissen wird durch Abwesenheit modelliert. Kein Eintrag für jede Proposition des Falls. Eine fehlende Haltung ist nicht dasselbe wie explizite Unsicherheit.

Keine numerische Confidence. Keine Felder für Lüge, Äußerung, Sprecherabsicht oder eine zu sagende Antwort.

## 7. Verpflichtende, begrenzte Provenance

Jeder Awareness- und Attitude-Eintrag hat genau eine primäre Herkunftsannotation:

```text
Provenance =
  { kind: "prior_knowledge" }
  | { kind: "witnessed_event", eventId: EventId }
  | { kind: "observed_evidence", evidenceId: EvidenceId }
  | { kind: "told_by_person", personId: PersonId }
  | { kind: "author_modeled_inference" }
```

`author_modeled_inference` ersetzt den Draft-Namen `authored_inference`. Der alte Diskriminator wird abgelehnt. Die neue Bezeichnung bedeutet nur: Der Autor hat diesen subjektiven Zustand als abgeleitet modelliert. Sie behauptet weder maschinelle Ableitung noch logische Gültigkeit.

Begründung der Pflicht: Ein Eintrag soll nicht ohne erkennbare Autorenentscheidung entstehen. Die Annotation bleibt klein; es gibt keine Quellensammlung, Beweiskette oder rekursive Provenance.

Referenz und Quelle müssen existieren. Darüber hinaus gilt:

- `prior_knowledge`: Zustand bestand bereits am Fallnullpunkt.
- `witnessed_event`: direkte Wahrnehmung während des bezeichneten Events.
- `observed_evidence`: Bezug auf tatsächlich modellierte Evidence; keine Interpretation ihrer Links.
- `told_by_person`: deklarierte Quelle; kein Abgleich mit deren Wissen, Ehrlichkeit oder NPC-Snapshot.
- `author_modeled_inference`: ausdrückliche manuelle Zuschreibung, ohne vorausgesetzte Inferenz-Engine.

Provenance ist eine Autorenannotation über den Erwerb, nicht zwingend die vom NPC selbst erkannte Quelle. Sie erteilt keine Awareness- oder Attitude-Freigaben und erscheint niemals in der Projektion.

Ein Quellenobjekt muss nicht zusätzlich in `awareness` stehen. Weder die Quelle noch ihre Eigenschaften dürfen dadurch automatisch sichtbar werden.

## 8. Zeit und Snapshot-Versionierung

- `asOf` ist der Zeitpunkt des gesamten Zustands.
- `acquiredAt` ist der Erwerbs- oder Annahmezeitpunkt genau des aktuell gespeicherten Eintrags.
- Für jeden Eintrag gilt `acquiredAt <= asOf`.
- `prior_knowledge` verlangt `acquiredAt === 0`; das bedeutet am Nullpunkt schon vorhanden, nicht zwingend ursprünglich genau dort gelernt.
- Bei `witnessed_event` und Instant muss `acquiredAt === event.time.at` gelten.
- Bei `witnessed_event` und Intervall muss `start <= acquiredAt && acquiredAt < end` gelten.
- Für die drei übrigen Herkunftsarten gibt es keine zusätzliche Zeitregel.
- Keine Addition, Rundung oder Epsilon-Verschiebung von Ticks.

Witness-Provenance verlangt keine Mitgliedschaft in `participantIds`: Das vorhandene Modell besitzt kein Sichtbarkeits- oder Wahrnehmungsmodell. Es wird ebenso wenig eine Event-Ende-Kenntnis aus Beobachtung während eines Intervalls abgeleitet.

Die Erwerbsannotation beweist keine Wahrnehmungs- oder Vorhersagefähigkeit. Claim-Zeitpunkte sind vom Erwerbszeitpunkt getrennt; V1 erfindet keine zusätzliche globale Verfügbarkeitsregel für Weltfakten.

`revision` ist eine positive sichere Ganzzahl. Sie wird nicht mit `asOf` gleichgesetzt. Gleicher Zeitpunkt mit anderer Revision ist zulässig. Reihenfolge oder Monotonie mehrerer Snapshots werden nicht geprüft.

Neue Haltungen werden durch separat authored, vollständige Snapshots ausgedrückt. Alte Snapshots bleiben unverändert. Es gibt kein History-Log, keine automatische Fortschreibung und keinen Query-Zeitparameter in der Projektion.

Ein früherer Zustand darf nicht durch Filtern eines neueren Snapshots nach `acquiredAt` rekonstruiert werden: entfernte oder ersetzte Haltungen wären verloren.

## 9. Exakte Statement-Eindeutigkeit

Pro NPC-Snapshot höchstens ein Awareness-Eintrag je Paar `(subject.kind, subject.id)`.

Für Attitudes zählt der strukturelle Sachverhalt, nicht allein die referenzierte ID:

1. Referenz gegen die gebundene Truth oder Solution auflösen.
2. Ausschließlich das zugehörige `claim`-Objekt betrachten.
3. Dessen Feldnamen aufsteigend nach UTF-16-Codeeinheiten sortieren.
4. Einen Schlüssel als JSON aus `[subject.kind, sortedEntries]` bilden, wobei jedes Entry `[fieldName, fieldValue]` ist.
5. Doppelte Schlüssel ablehnen, unabhängig von Stance, Polarität, Zeitpunkt oder Provenance.

Alle tatsächlich vorhandenen Claim-Felder sind Skalare. Der Schlüssel umfasst den Claim-Diskriminator und sämtliche definierten Felder. Proposition-ID, Conclusion-ID und objektiver Wahrheitswert gehören nicht dazu.

Damit gelten zwei verschiedene Proposition-IDs mit gleichem `personAt`-Claim als derselbe epistemische Sachverhalt. Änderungen an Person, Ort, Zeitpunkt, Event, Gegenstand, Rolle oder behauptetem Facettenwert ergeben unterschiedliche Claims.

Der Statement-Namespace ist Teil des Schlüssels. Es gibt keine logische Äquivalenzprüfung über verschiedene Claim-Arten hinweg.

TASK-0003 verbietet strukturell doppelte Conclusions bereits. TASK-0004 verwendet trotzdem dieselbe strukturelle Regel für beide Subject-Arten; sie ersetzt keine Solution-Validierung.

Keine stille Zusammenführung, keine Bevorzugung des letzten Eintrags. Gleichzeitige Gegenpositionen zum selben Claim innerhalb eines NPC-Snapshots werden durch einen passenden `uncertain`-Eintrag modelliert. Unterschiedliche NPCs dürfen gegensätzliche Haltungen besitzen.

## 10. Projektion und Spoiler-Isolation

### 10.1 Öffentlicher Einstieg und genaue Ausgabe

```text
projectNpcKnowledge(
  snapshot: NpcKnowledgeSnapshot,
  truth: CaseTruth,
  solution: CaseSolution | null
) -> ProjectionResult

ProjectionResult =
  { success: true, context: NpcVisibleContext }
  | { success: false, code: "CONTEXT_BINDING_MISMATCH" }

VisibleKind =
  "person" | "location" | "item" | "event" |
  "evidence" | "proposition" | "conclusion"

VisibleRef<K extends VisibleKind = VisibleKind> = {
  kind: K,
  index: positive safe integer
}

NpcVisibleContext = {
  schemaVersion: 1,
  asOf: Tick,
  self: VisibleRef<"person">,
  awareness: VisibleRef<AwarenessKind>[],
  attitudes: {
    subject: VisibleRef<"proposition" | "conclusion">,
    claim: NpcVisibleClaim,
    stance: EpistemicStance
  }[]
}
```

`AwarenessKind` bezeichnet hier die ersten fünf Kategorien, keine zusätzliche exportierte API.

Bei Bindungsfehler genau das angegebene Fehlerobjekt zurückgeben: kein Teilkontext, keine Hashes, IDs oder Diagnose-Nachricht. Die Funktion arbeitet ausschließlich mit geparsten, nominalen Inputs; Umgehung durch unsichere Casts ist keine unterstützte Eingabeform.

Erfolgreiche Ausgabe enthält genau die aufgeführten Felder. `self` ist die lokale Referenz des NPC. `awareness` enthält ausschließlich die expliziten Awareness-Einträge. In Claims genannte Entitäten werden nicht zusätzlich in `awareness` eingetragen.

### 10.2 Deterministische lokale Handles

Lokale Handles sind für V1 erforderlich: Sprechende IDs wie `event:ben-kills-clara` dürfen nicht als Klartext den Kontext verlassen. Die Handles sind projektionslokale Bezeichner, keine globalen Identitäten.

Algorithmus, exakt in dieser Reihenfolge:

1. Sämtliche Bindungen prüfen; bei Fehler abbrechen.
2. Die sichtbare Referenzmenge bilden, bestehend ausschließlich aus:
   - dem NPC selbst;
   - expliziten Awareness-Subjects;
   - expliziten Attitude-Subjects;
   - Entitätsreferenzen in den Claims genau dieser Attitudes.
3. Nach Kategorie gruppieren und identische rohe IDs innerhalb einer Kategorie deduplizieren.
4. Pro Kategorie nur diese sichtbaren IDs aufsteigend nach UTF-16-Codeeinheiten sortieren. Vergleich mit `<` und `>`; kein `localeCompare`.
5. Pro Kategorie die Indizes `1..N` vergeben. Derselbe Referent erhält überall dasselbe Paar `{kind,index}`.
6. Awareness sortieren nach fester Kategorie-Reihenfolge und anschließend numerischem Index.
7. Attitudes sortieren nach Kategorie des Subjects und anschließend numerischem Index.

Feste Kategorie-Reihenfolge:

```text
person, location, item, event, evidence, proposition, conclusion
```

Die Vergabe hängt weder von Source-Collection-Reihenfolgen noch von nicht freigegebenen Entitäten ab. Provenance-Referenzen werden nicht in die sichtbare Menge aufgenommen.

Die interne Zuordnung bleibt lokal innerhalb des Aufrufs. Keine Reverse-Mapping-Tabelle, kein Resolver, kein Callback und keine Quellobjekt-Referenz werden ausgegeben. Handles können sich bei anderem sichtbarem Inhalt ändern und dürfen nicht snapshotübergreifend als stabile IDs behandelt werden.

Diese Garantie verhindert die Ausgabe roher IDs und unbekannter Datensätze. Sie ist kein Anspruch auf kryptografische Anonymisierung gegenüber bereits außerhalb des Systems vorhandenem Wissen.

### 10.3 Exhaustive Claim-Freigabe

Die folgenden neun Formen sind die gesamte `NpcVisibleClaim`-Union. Die Kürzel `P`, `L`, `I` und `E` stehen für die entsprechende `VisibleRef`-Kategorie.

| Quell-Claim | Exakte sichtbare Felder |
|---|---|
| Proposition `personAt` | `{kind:"personAt", person:P, location:L, at:Tick}` |
| Proposition `eventHasParticipant` | `{kind:"eventHasParticipant", event:E, person:P}` |
| Proposition `eventHasItem` | `{kind:"eventHasItem", event:E, item:I}` |
| Conclusion `personResponsibleForEvent` | `{kind:"personResponsibleForEvent", person:P, event:E}` |
| Conclusion `personRoleForEvent` | `{kind:"personRoleForEvent", person:P, event:E, role:ResponsibilityRole}` |
| Conclusion `noPersonResponsibleForEvent` | `{kind:"noPersonResponsibleForEvent", event:E}` |
| Conclusion `eventCausedEvent` | `{kind:"eventCausedEvent", causeEvent:E, event:E}` |
| Conclusion `eventIntent` | `{kind:"eventIntent", event:E, value:Intent}` |
| Conclusion `eventMechanism` | `{kind:"eventMechanism", event:E, value:Mechanism}` |

Die Werte `role`, `Intent` und `Mechanism` beschreiben ausschließlich den freigegebenen Claim, keine aus der Resolution ergänzte Wahrheit. Die dazugehörige Stance bleibt erhalten.

`claim.at` ist ausdrücklich autorisierter Aussageinhalt. `asOf` ist Snapshot-Zeit. Beide sind von dem verbotenen `acquiredAt` verschieden.

Ausgabeobjekte pro Variante explizit aufbauen. Kein Object-Spreading von Domain-Objekten und kein generisches Herauslöschen einiger Geheimfelder aus vollständigen Objekten. Die Transformation muss exhaustiv über die vorhandenen Claim-Varianten sein; zukünftige Varianten werden nicht automatisch freigegeben.

Stance ebenfalls ausschließlich mit den erlaubten Feldern `kind/value` beziehungsweise `kind/leaning` rekonstruieren. Es wird kein objektiver Status hinzugefügt.

### 10.4 Verbotene Information und Freigabegrenze

Niemals projizieren:

- rohe Domain-IDs, `caseId`, `npcId`, `truthHash`, `solutionHash` oder Snapshot-Revision;
- `Proposition.truth`, kanonischen Conclusion-Status oder `isMistaken`;
- Resolution, objektive Responsibility-Assignments oder `requiredConclusions`;
- Secrets, Motive und Relationships;
- Event- oder Evidence-Beschreibungen;
- Personen-, Orts- oder Gegenstandsnamen;
- Provenance oder `acquiredAt`;
- vollständige Event-Zeit, Teilnehmer-, Gegenstands- oder Ursachenlisten;
- Evidence-Quellen und Evidence-Links;
- weitere unbekannte Entitäten, eine Reverse-Map oder eingebettete Quellobjekte.

Eine explizit freigegebene subjektive Responsibility-Conclusion ist zulässig; das objektive `responsibility`-Objekt ist es nicht. Ebenso ist `stance.value` subjektiver Inhalt, kein kopiertes `Proposition.truth`.

Bare Awareness gibt nur einen bekannten Referenten frei. Sie erzeugt keine zusätzlichen Aussagen über ihn. Der Kontext ist absichtlich noch kein menschenlesbarer Dialogprompt.

Die Informationsbarriere ist eine Ausgabegarantie innerhalb des vertrauenswürdigen Domain-Codes, keine Prozess-Sandbox. Ein späterer Verbraucher darf nur den erfolgreichen sichtbaren Kontext erhalten, keinen Autoren-Snapshot, keine Zod-Diagnostik und keinen zusätzlichen Zugriff auf Truth oder Solution. Dieser Task baut solche Verbraucher oder Zugriffswege nicht.

## 11. Referenzprüfung, Konsistenz und Unveränderlichkeit

Prüfen:

1. Strikte Form und gültige bestehende IDs, Ticks, Version und Revision.
2. Bindung nach Abschnitt 5, bevor kontextabhängige Referenzen ausgewertet werden.
3. NPC, alle Awareness-Subjects und alle Herkunftsreferenzen existieren in der richtigen Collection.
4. Jede Proposition-Attitude referenziert eine vorhandene Proposition.
5. Jede Conclusion-Attitude referenziert eine Conclusion der ausdrücklich gebundenen Solution.
6. Zeitregeln aus Abschnitt 8.
7. Eindeutigkeit aus Abschnitt 9.
8. Faktivität von Proposition-`knowledge`.
9. Keine Conclusion-`knowledge`.

Fehlende Referenzen müssen Zod-Fehler mit betroffenem Eingabepfad erzeugen. Vor abhängigen Zugriffen Referenzen auflösen und Fehler behandeln; kein Zugriff auf `undefined`, keine unbeabsichtigte Exception in `.safeParse`.

Nicht prüfen:

- räumliche oder kausale Plausibilität subjektiver Überzeugungen;
- logische Vereinbarkeit verschiedener, nicht identischer Claims;
- Glaubwürdigkeit von Evidence oder Wahrheit einer erzählenden Person;
- Soundness einer `author_modeled_inference`;
- objektiven Conclusion-Status;
- Weltkonsistenz erneut.

`validateCaseSemantics` wird nicht intern aufgerufen und nicht auf NPC-Beliefs angewandt. `Secret`, Event-Teilnahme, Evidence-Links und Solution-Zuordnungen erzeugen weder Awareness noch Attitudes.

Beide Parsing-Einstiege müssen einen vollständig vom Input entkoppelten, nominal mit `NpcKnowledgeSnapshot` markierten und tief eingefrorenen Snapshot erzeugen. Alle verschachtelten Arrays und Objekte sind readonly. Der Input bleibt veränderbar.

Truth und Solution werden weder geändert noch erneut eingefroren. Der Snapshot enthält keine Kopie beider Dokumente. Die Projektion erzeugt eigene erlaubte Objekte, ohne veränderliche oder versteckte Referenzen auf Domain-Objekte.

## 14. Adversarial Tests der Informationsbarriere

1. **Exakte Handles:** Eine Fixture mit mehreren sichtbaren Referenten je Kategorie erhält handgeschriebene erwartete Indizes und Ausgabe-Reihenfolgen. Eine Person in `self`, Awareness und Claim bekommt dieselbe lokale Referenz.
2. **Permutation:** Source-Collections, NPC-Collections und Object-Property-Reihenfolgen permutieren. Das vollständige Projektionsresultat bleibt identisch.
3. **Unbekannte Entitäten:** Nicht freigegebene Personen/Events mit lexikografisch früheren IDs ergänzen. Nach korrektem Neuparsen und Umbinden bleiben alle sichtbaren Handles unverändert.
4. **Sprechende IDs:** Lösungsbezogene Marker in IDs verwenden. Weder diese vollständigen IDs noch eine Reverse-Map erscheinen in der serialisierten Projektion.
5. **Freitext-Spoiler:** Marker in Event-/Evidence-Beschreibungen und Personen-/Orts-/Gegenstandsnamen eintragen. Awareness oder referenzierte Claims dürfen die Marker nicht transportieren.
6. **Verborgene Autorendaten:** Nicht freigegebene Resolution-Facetten, erforderliche Antworten, Secrets, Motive, Relationships, Evidence-Links und Ursachen ändern. Bei identischem freigegebenem Claim-Inhalt und gültig erneuerter Bindung bleibt der Kontext gleich.
7. **Objektiver Irrtum unsichtbar:** Für identische Proposition-Beliefs `Proposition.truth` zwischen zwei gültigen Kontexten ändern. Nach Neubindung identische sichtbare Ausgabe; kein Richtig/Falsch-Indikator.
8. **Conclusion-Status unsichtbar:** Dieselbe Conclusion-Belief gegen passend erzeugte Solutions mit wahrer, falscher und nicht festgelegter Zuordnung projizieren. Keine Änderung des freigegebenen Claims oder der Stance.
9. **Provenance bleibt privat:** Herkunft, Quellen-IDs und zulässige Erwerbszeiten ändern, `asOf` und freigegebene Inhalte beibehalten. Identischer Kontext; Quellen tauchen nicht als zusätzliche Handles oder Awareness auf.
10. **Weder Gleichsetzung noch Verwechslung:** `stance.value` und `claim.at` bleiben erlaubt, während objektives `truth` und `acquiredAt` fehlen. Nicht nur nach Feldnamen löschen; genaue Ausgabeformen testen.
11. **Kontexttausch:** Einen geparsten Snapshot mit einer anderen Truth oder Solution an die Projektion geben. Ausschließlich das exakte Fehlerresultat, ohne Teilobjekt oder Diagnosewerte.
12. **Vollständige Allowlist:** Alle neun Claims gegen handgeschriebene Ausgaben testen. Zusätzliche Property-Leaks lassen den Test fehlschlagen.
13. **Keine Referenz-Leaks:** Ausgaben rekursiv nur auf erlaubte JSON-Daten prüfen; keine Symbole, Funktionen, Getter, versteckten Properties oder Quellobjekt-Identitäten.
14. **Keine automatische Zuteilung:** Beteiligung an einem Event, Secret-Mitgliedschaft oder Evidence-Unterstützung allein erzeugt keine NPC-Einträge.
15. **Snapshot statt History:** Eine ersetzte oder entfernte Haltung lässt sich nur aus dem alten Snapshot projizieren; die neue Projektion enthält sie nicht. Kein Query-Zeitparameter.

Metamorphe Tests verwenden jeweils neu geparste, korrekt gebundene Snapshots. Sie dürfen Bindungsprüfungen nicht umgehen. Knowledge-Polarität muss in jedem akzeptierten Kontext weiterhin stimmen; Statuswechsel-Tests verwenden deshalb Beliefs.

Die Tests der Barriere garantieren Datenminimierung für diese API. Sie behaupten keine Isolation eines zukünftigen Prozesses, der zusätzlich direkten Zugriff auf das Repository oder Domain-Objekte erhält.
